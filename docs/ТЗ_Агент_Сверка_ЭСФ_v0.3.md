## 1. Цель и контекст

### 1.1. Проблема
Бухгалтер аутсорсинговой компании ведёт N баз «Бухгалтерия для Казахстана». Перед закрытием периода и сдачей ФНО 300.00 нужно убедиться, что данные поступлений в 1С совпадают с ЭСФ поставщиков. На практике:

- часть поступлений не связана с ЭСФ или связана с неверной;
- при совпадении итогов расходятся строки (номенклатура, количество, цена);
- есть расхождения в копейках из-за округления (построчное vs итоговое, НДС «сверху» vs «в том числе»), которые накапливаются и дают расхождение в декларации;
- существующие обработки находят часть проблем, но не объясняют причину и не предлагают исправление; проверка остаётся ручной и занимает часы на каждую базу.

### 1.2. Цель MVP
Дать бухгалтеру инструмент, который по запросу на естественном языке:
1. находит все расхождения между поступлениями и ЭСФ за период — на уровне документов **и строк**, с учётом допусков на округление;
2. классифицирует каждое расхождение и объясняет вероятную причину;
3. предлагает исправление и применяет его только после подтверждения бухгалтера;
4. создаёт недостающие документы (поступление по ЭСФ, корректировку) в виде черновиков с умным подбором номенклатуры и пометками уверенности;
5. показывает, откуда взята каждая цифра (кликабельные ссылки на документы).

### 1.3. Критерии успеха пилота
- Полнота: агент находит ≥ 95 % расхождений, которые бухгалтер нашёл бы вручную (проверяется параллельным прогоном на реальных базах).
- Точность: ≤ 10 % ложных срабатываний после настройки допусков.
- Время проверки одной базы за квартал сокращается минимум в 3 раза.
- Ни одного случая изменения данных без явного подтверждения пользователя.
- При создании поступления по ЭСФ ≥ 80 % строк заполняются без ручной правки (номенклатура, счёт учёта, договор).

### 1.4. Что НЕ входит в MVP
- Реализации и исходящие ЭСФ (сценарий 2).
- Автозаполнение и проверка ФНО 300.00 (сценарий 3).
- Ответы на уведомления КГД (сценарий 4).
- Прямые вызовы ИС ЭСФ — MVP работает с данными, уже загруженными в базу 1С (при необходимости используется штатная загрузка ЭСФ).
- Поддержка конфигураций кроме «Бухгалтерия для Казахстана», ред. 3.0.

## 2. Термины

| Термин | Значение |
|---|---|
| Поступление | Документ «Поступление ТМЗ и услуг» (и при необходимости «Поступление доп. расходов», «Авансовый отчёт») |
| ЭСФ | Документ «Электронный счёт-фактура (полученный)» в базе 1С, загруженный из ИС ЭСФ или введённый вручную |
| Связь | Ссылка между поступлением и ЭСФ (реквизит «Документ-основание» у ЭСФ / табличная часть связей) |
| Пара | Поступление + связанная с ним ЭСФ, участвующие в сверке |
| Расхождение | Любое несовпадение между парой (или отсутствие пары), превышающее допуск |
| Допуск | Максимально допустимая разница суммы, считаемая округлением |
| Инструмент (tool) | Экспортная функция расширения, которую агент может вызвать |
| Агент | Связка LLM + оркестратор, которая выбирает и вызывает инструменты и формирует ответ |

## 3. Архитектура

```
┌──────────────────────────────┐        HTTPS        ┌──────────────────────────┐        ┌─────────┐
│  1С: Бухгалтерия для РК      │ ◄─────────────────► │  Оркестратор (сервис)    │ ◄────► │   LLM   │
│  + Расширение «Агент»        │   HTTP-сервис /     │  - цикл tool calling     │        │ (API)   │
│    - HTTP-сервис             │   фоновый поллинг   │  - база знаний (RAG)     │        └─────────┘
│    - инструменты (tools)     │                     │  - журнал, маскирование  │
│    - движок сверки           │                     │  - лимиты, очередь       │
│    - форма «Агент» (UI)      │                     └──────────────────────────┘
└──────────────────────────────┘
```

### 3.1. Принципы
1. **Расширение, а не изменение типовой.** Все объекты — в расширении конфигурации; обновление типовой не должно ломать продукт.
2. **Модель не считает, модель объясняет.** Сопоставление, допуски, суммы — детерминированный код в 1С. LLM получает готовые результаты, выбирает, что проверить дальше, и формулирует ответ.
3. **Модель не имеет прямого доступа к базе.** Только вызов разрешённых инструментов с типизированными параметрами. Никаких произвольных запросов.
4. **Чтение по умолчанию, запись — только с подтверждением.** Инструменты записи возвращают «план изменений», который пользователь применяет кнопкой.
5. **Прозрачность.** Каждый ответ содержит список вызванных инструментов и ссылки на документы.
6. **Минимум данных наружу.** В оркестратор уходят результаты инструментов; режим маскирования заменяет наименования контрагентов и номенклатуры на идентификаторы.

### 3.2. Транспорт
Два режима, выбираются в настройках расширения:
- **Прямой**: оркестратор вызывает HTTP-сервис расширения (для серверных баз с доступным адресом).
- **Обратный (поллинг)**: фоновое задание в 1С периодически забирает задачи из очереди оркестратора и отправляет результаты (для файловых баз и баз за NAT). Интервал — 5–15 с во время активного диалога.

Авторизация — токен базы + подпись запроса. Один оркестратор обслуживает много баз (multi-tenant), каждая база изолирована.

## 4. Движок сверки (ядро, код 1С)

### 4.1. Формирование пар

Вход: организация, период, опционально контрагент.

1. Выбрать все поступления за период (проведённые; непроведённые — отдельным списком «требуют внимания»).
2. Выбрать все полученные ЭСФ, у которых дата оборота или дата выписки попадает в период, плюс ЭСФ за период «хвоста» (по умолчанию +20 дней после конца периода — срок выписки ЭСФ).
3. Построить пары по явной связи (документ-основание).
4. Для поступлений без связи — попытаться найти кандидата-ЭСФ: тот же контрагент (БИН), та же сумма с НДС в пределах допуска, дата оборота ±N дней. Результат — «предполагаемая связь», требующая подтверждения.
5. Для ЭСФ без связи — аналогично искать поступление-кандидата.
6. Остаток — «ЭСФ без поступления» и «поступление без ЭСФ».

### 4.2. Сверка на уровне документа
Для каждой пары сравнить:
- контрагент (БИН);
- дата оборота ЭСФ vs дата поступления (расхождение > 0 дней — информационно; разные периоды НДС — ошибка);
- ставка НДС (по строкам и итогу);
- сумма без НДС, сумма НДС, сумма с НДС — с учётом допуска;
- валюта и курс (если не KZT);
- статус ЭСФ (аннулирована / отозвана / исправленная / дополнительная — должна быть учтена корректно);
- номер и дата ЭСФ в реквизитах поступления (если заполняются).

### 4.3. Сверка на уровне строк
Сопоставление строк поступления и строк ЭСФ — многоуровневое:

| Уровень | Ключ сопоставления | Уверенность |
|---|---|---|
| 1 | Номенклатура по явному соответствию (справочник соответствий номенклатуры контрагента, если ведётся) | высокая |
| 2 | Нормализованное наименование (нижний регистр, без лишних пробелов/знаков, единицы измерения) + количество + цена | высокая |
| 3 | Количество + цена + ставка (наименования различаются) | средняя |
| 4 | Сумма строки + ставка (количество/цена различаются) | низкая |
| 5 | Нечёткое совпадение наименования (расстояние Левенштейна / n-граммы) + сумма в допуске | низкая |

Результат по строке — одно из:
- **совпадает**;
- **совпадает в пределах допуска** (разница в копейках);
- **расхождение по цене / количеству / сумме / ставке / единице измерения**;
- **строка есть только в поступлении**;
- **строка есть только в ЭСФ**;
- **одна строка против нескольких** (например, в ЭСФ разбито по партиям).

### 4.4. Расхождения в копейках — отдельный блок

Отдельно определяется **источник** копеечной разницы, потому что он определяет исправление:

| Код | Источник | Признак | Рекомендуемое действие |
|---|---|---|---|
| R1 | Построчное округление НДС vs от итога | Сумма построчного НДС ≠ НДС от итога, разница ≤ 0,01 × число строк | Допуск; при необходимости корректировка суммы НДС в строке |
| R2 | НДС «в том числе» vs «сверху» | Цена в 1С включает НДС, в ЭСФ — нет (или наоборот), разница в копейках на строку | Изменить флаг «Сумма включает НДС» в поступлении |
| R3 | Округление цены | Цена в ЭСФ с 4+ знаками, в 1С — 2 знака | Привести цену к значению из ЭСФ / уточнить точность цены |
| R4 | Перенос остатка округления на последнюю строку | Все строки совпадают, кроме одной на 0,01–0,05 | Принять ЭСФ как эталон, скорректировать строку |
| R5 | Пересчёт валюты | Разный курс / дата курса | Проверить дату курса |
| R6 | Необъяснимая разница | Ни один паттерн не подходит | Ручной разбор |

**Допуски** (настраиваемые, по умолчанию):
- на строку: 0,01 × количество, но не более 1,00 ₸;
- на документ: 0,01 × число строк, но не более 5,00 ₸;
- порог «считать существенным» для итогов периода: 1,00 ₸.

Всё, что в допуске, **не считается ошибкой**, но отображается в отчёте отдельной группой «округления» с суммой накопленной разницы по периоду — именно она объясняет хвост в декларации.

| Код | Описание | Критичность |
|---|---|---|

| D02 | Поступление без ЭСФ (срок истёк) | высокая |
| D03 | ЭСФ без поступления | высокая |
| D04 | Найдена предполагаемая связь, не установлена | средняя |
| D05 | Разная ставка НДС | высокая |
| D06 | Расхождение суммы НДС выше допуска | высокая |
| D07 | Расхождение суммы без НДС выше допуска | высокая |
| D08 | Разные периоды НДС (дата оборота ЭСФ в другом квартале) | высокая |

## 5. Инструменты (API расширения для агента)

Все инструменты — экспортные функции общего модуля расширения, опубликованные через HTTP-сервис. Параметры и результат — JSON. Каждый вызов логируется.

Детальные контракты (структуры запроса и ответа, коды ошибок, транспорт, маскирование) — в отдельном документе «Приложение А. Контракты инструментов». Таблицы ниже дают состав инструментов; при расхождении с Приложением А верным считается Приложение.

### 5.1. Чтение

| Инструмент | Параметры | Возвращает |
|---|---|---|
| `ПолучитьКонтекст` | — | организации, текущий период, статус закрытия, релиз конфигурации, валюта учёта |
| `СверитьПериод` | организация, дата_начала, дата_конца, контрагент?, порог_критичности? | сводка: число пар, число расхождений по кодам, накопленная разница округлений, список ID расхождений |
| `ПолучитьРасхождение` | id_расхождения | полная карточка: пара, код, сравнение полей, построчное сопоставление, вероятная причина (R-код), рекомендуемое действие |
| `ПолучитьСписокРасхождений` | организация, период, фильтр (коды, контрагент, критичность), страница | постраничный список |
| `ПолучитьДокумент` | ссылка | шапка + строки поступления или ЭСФ |
| `НайтиКандидатовЭСФ` | ссылка_поступления, допуск_дней, допуск_суммы | список ЭСФ-кандидатов с оценкой совпадения |
| `НайтиКандидатовПоступления` | ссылка_ЭСФ, … | аналогично |
| `ПолучитьКарточкуКонтрагента` | БИН | реквизиты, признак плательщика НДС на дату, дата постановки/снятия, серия/номер свидетельства |
| `ПолучитьОборотыНДС` | организация, период | обороты по зачёту НДС в разрезе ставок (для сверки итога с суммой по ЭСФ) |

**Что сознательно не вошло.** Инструмент «ПолучитьИсториюИзменений» (версии документа) исключён из MVP: он требует включённого версионирования объектов, которое у большинства клиентов аутсорсинга выключено — оно раздувает базу, и в половине баз инструмент возвращал бы пустоту. Сверке история не нужна: сопоставление, привязка и создание документов смотрят на текущее состояние. Отвечать на вопрос «кто и когда это поменял» потребуется при разборе уведомлений КГД — то есть в сценариях 3–4, туда он и отложен.

История действий самого агента к этому не относится: она обязательна и обеспечивается отдельным журналом (п. 7 и инструмент `get_journal` Приложения А) — бухгалтер должен видеть, что сделал агент и чем это откатить.

### 5.2. Запись (двухфазные)

| Инструмент | Фаза 1 — план | Фаза 2 — применение |
|---|---|---|
| `УстановитьСвязь` | показать пару «поступление ↔ ЭСФ» | записать связь |
| `СкорректироватьСтроки` | показать diff по строкам (было / станет), перечень затрагиваемых проводок | изменить строки, перепровести |
| `ИзменитьПризнакНДС` | показать пересчёт сумм при смене «в т.ч./сверху» | применить |
| `СоздатьКорректировку` | показать проект документа корректировки поступления | создать документ (не проводить) |
| `ПометитьПроверено` | — | пометка «расхождение рассмотрено, принято» с комментарием |
| `СоздатьПоступлениеПоЭСФ` | показать заполненный черновик поступления: контрагент, договор, склад, строки с подобранной номенклатурой, счетами учёта, ставкой; по каждому полю — уровень уверенности и альтернативы | создать документ (непроведённый), установить связь с ЭСФ |
| `СоздатьПоступленияМассово` | по списку ЭСФ без поступлений (D03) — сводная таблица черновиков с числом «неуверенных» строк в каждом | создать пачку непроведённых документов, общий список для просмотра |

### 5.2.1. Подбор номенклатуры при создании по ЭСФ

Для каждой строки ЭСФ, по убыванию приоритета:
1. справочник соответствий номенклатуры контрагента (если ведётся) — уверенность высокая;
2. история: та же строка (нормализованное наименование + контрагент) уже сопоставлялась в прошлых поступлениях — высокая;
3. точное совпадение нормализованного наименования с элементом справочника «Номенклатура» — высокая;
4. нечёткое совпадение (n-граммы / Левенштейн) с порогом — средняя, показать 3 альтернативы;
5. не найдено — строка помечается «создать новую номенклатуру?» с предзаполненным наименованием, единицей, ставкой — низкая.

Счёт учёта и вид номенклатуры — по настройкам счетов учёта номенклатуры типовой; договор — основной договор контрагента или единственный действующий; при неоднозначности — пометка и выбор.

Каждое подтверждённое бухгалтером сопоставление записывается в справочник соответствий — агент учится на базе клиента.

Правила:
- Фаза 2 вызывается только из интерфейса 1С нажатием кнопки пользователем; агент не может вызвать её сам.
- Перед фазой 2 проверяется: период не закрыт, документ не в закрытом периоде, у пользователя есть права.
- Каждое применение пишет запись в журнал изменений агента (кто, когда, что, по какому расхождению).
- Созданные документы — только непроведённые; проведение — отдельное явное действие пользователя по конкретному документу.
- Создание в закрытом периоде запрещено.
- Созданный документ получает пометку «Создан агентом» (реквизит расширения + ссылка на диалог), чтобы пачку можно было найти и откатить.
- Отдельная роль «Агент: создание документов».

### 5.3. Служебные
- `ПолучитьНастройки` / `СохранитьНастройки` — допуски, режим маскирования, хвост периода.
- `ОткрытьОбъект` — возвращает навигационную ссылку для клика в ответе.

## 6. Агент и диалог

### 6.1. Поведение
- Язык диалога — русский (позже казахский).
- Агент всегда начинает с `ПолучитьКонтекст`, затем выбирает инструменты под запрос.
- Ограничение: не более 30 вызовов инструментов на один запрос; при превышении — вернуть промежуточный результат и спросить, продолжать ли.
- Агент никогда не называет число, которого нет в результате инструмента. Если данных нет — говорит об этом.
- В конце ответа — блок «Что я проверил» (список вызовов) и блок «Что предлагаю сделать» (кнопки применения).

### 6.2. Типовые запросы MVP
1. «Сверь поступления и ЭСФ за 2 квартал по ТОО X».
2. «Почему НДС к зачёту по базе отличается от суммы по ЭСФ на 3,47 тенге?»
3. «Покажи поступления без ЭСФ, у которых срок выписки уже прошёл».
4. «Что не так с поступлением № 145 от 14.05?»
5. «Найди, к какой ЭСФ относится это поступление».
6. «Какие контрагенты за квартал слетели с НДС?»
7. «Исправь копеечные расхождения по паттерну R1, покажи что изменится».
8. «Создай поступление по этой ЭСФ».
9. «По всем ЭСФ за июль без поступлений подготовь черновики и покажи, где не уверен».

### 6.3. База знаний (RAG)
На MVP — небольшая: правила выписки ЭСФ (сроки, исправленная/дополнительная/аннулированная), правила зачёта НДС по НК РК (ст. 400–403), типовые причины расхождений в 1С. Каждая ссылка в ответе — на статью/пункт.

### 6.4. Маскирование
В режиме маскирования оркестратор перед отправкой в LLM заменяет: наименования контрагентов, БИН, наименования номенклатуры, номера документов → на стабильные псевдонимы в рамках сессии; обратная подстановка при выводе пользователю. Суммы и даты не маскируются.

## 7. Интерфейс в 1С

- Форма «Агент» (подсистема «Агент бухгалтера»): поле ввода, история диалога, область ответа с таблицами и кликабельными ссылками, панель «Предложенные действия» с кнопками «Применить» / «Отклонить».
- Обработка «Сверка поступлений и ЭСФ» — классический отчёт на СКД поверх того же движка (без ИИ), для тех, кто хочет просто таблицу. Группировки: контрагент → документ → строка; отбор по кодам расхождений; итоги округлений.
- Кнопка «Спросить агента» в формах поступления и ЭСФ — открывает диалог с контекстом документа.
- Журнал действий агента — отдельный регистр сведений + список.

## 8. Нефункциональные требования

| Требование | Значение |
|---|---|
| Платформа | 8.3.20+ (уточнить минимум по парку баз пилота) |
| Конфигурация | Бухгалтерия для Казахстана 3.0, релизы за последние 12 месяцев |
| Режим | Файловый и клиент-серверный |

| Время ответа агента | Простой запрос ≤ 45 с, сверка периода ≤ 120 с (см. пояснение ниже) |
| Индикация ожидания | Начиная с 3-й секунды форма показывает текущий шаг: «читаю контекст базы», «сверяю период», «разбираю расхождение» |
| Безопасность | TLS; токен на базу; роли в 1С: «Агент: чтение», «Агент: применение изменений», «Агент: создание документов» |
| Журналирование | Все вызовы инструментов и все применённые изменения; хранение 12 мес |
| Обновляемость | Расширение с режимом совместимости; проверка применимости при смене релиза |
| Данные наружу | Только результаты инструментов; режим маскирования; договор об обработке данных |

---

**О времени ответа.** Норматив поднят относительно v0.2 (было 15 с на простой запрос) по результатам замеров на живой модели. Причина не в оптимизации, а в устройстве агента: даже вопрос про один документ требует последовательной цепочки вызовов — контекст базы, расчёт периода, список расхождений, карточка, — и каждый шаг это отдельное обращение к модели по 5–10 с. Шаги нельзя выполнить параллельно: каждый следующий зависит от результата предыдущего. Замеры на подготовленных данных дали 27–57 с; обращение к реальной базе добавит время сверки.

Поэтому вместо недостижимого норматива вводится требование к индикации: пользователь видит, что происходит, и понимает, что система работает. Ожидание с видимым прогрессом воспринимается иначе, чем застывшая форма.
