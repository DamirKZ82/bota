# Бота — ИИ-агент бухгалтера для «1С:Бухгалтерия для Казахстана»

Сценарий 1 (MVP): сверка поступлений и полученных ЭСФ с поиском расхождений.
Техническое задание и Приложение А с контрактами инструментов — в [docs/](docs/).

Этот репозиторий — **оркестратор**: внешний сервис между базой 1С и языковой моделью.
Расширение 1С (движок сверки, HTTP-сервис, форма диалога) разрабатывается отдельно.

## Запуск

```bash
python -m venv .venv && .venv/Scripts/python -m pip install -e ".[dev]"
```

```bash
.venv/Scripts/python -m pytest
```

```bash
.venv/Scripts/uvicorn orchestrator.main:app --reload
```

По умолчанию (`TRANSPORT=mock`) оркестратор работает на мок-данных: ни базы 1С, ни
Postgres не нужно, диалоги живут в памяти. Рабочие режимы (`polling`, `direct`)
требуют Postgres и `ENCRYPTION_KEY` — см. `.env.example`.

Миграции применяются сами при старте; вручную — `python -m orchestrator.db.migrate`
(`--with-optional` добавит таблицы базы знаний, требующие pgvector).

Тесты БД идут на отдельной базе — они пересоздают схему целиком. Адрес берётся
из `BOTA_TEST_DSN` в `.env`; без него такие тесты пропускаются, и `pytest` всё
равно проходит.

Зарегистрировать базу 1С (токен печатается один раз, в БД ложится только его хеш):

```bash
.venv/Scripts/python -m orchestrator.db.register --id demo --name "Демо-база" --transport polling
```

Проверить реестр инструментов: `GET /v1/tools` — эта же выдача служит спецификацией
для разработчика расширения 1С.

Задать вопрос агенту:

```bash
curl -s -X POST http://localhost:8000/v1/chat/ask -H "Authorization: Bearer demo-token" -H "Content-Type: application/json" -d "{\"message\":\"Сверь поступления и ЭСФ за 2 квартал\"}"
```

## Устройство

```
orchestrator/
  agent/       цикл tool calling, системный промпт
  llm/         абстракция провайдера модели + адаптер Claude API
  tools/       контракты (Приложение А), реестр, исполнитель
  transport/   каналы до 1С: direct, polling, mock
  masking/     псевдонимизация данных перед отправкой в модель
  api/         маршруты FastAPI
  db/          схема, миграции, репозитории, шифрование
```

Четыре принципа, на которых держится код (ТЗ п.3.1):

1. **Модель не считает — модель объясняет.** Суммы, допуски и сопоставление — код в 1С.
   Оркестратор передаёт готовый результат и не пересчитывает его.
2. **Модель не имеет доступа к базе.** Только вызов инструментов из реестра с
   параметрами, проверенными контрактом. Произвольные запросы невозможны.
3. **Запись только с подтверждением.** Инструменты `plan_*` возвращают план изменений;
   применяет его пользователь кнопкой в 1С. Фазы 2 в реестре инструментов нет —
   агент физически не может её вызвать.
4. **Минимум данных наружу.** Маскирование выполняет расширение 1С: таблица
   псевдонимов живёт там, оркестратор соответствий не знает вовсе.

## Что хранится в базе, а что нет

В базе оркестратора нет наименований контрагентов, номенклатуры и номеров
документов — ни в открытом виде, ни в зашифрованном. Отображаемую историю диалога
ведёт форма «Агент» в 1С, тела планов изменений, кэш сверки и таблица псевдонимов
маскирования остаются в базе 1С. Здесь — рабочая история модели (а она уже в
псевдонимах), метаданные вызовов и агрегаты для метрик пилота.

Шифрование (AES-GCM) применяется к единственному значению: ключу подписи запросов
к базе 1С, который нужен в открытом виде для HMAC.
